# Сбор датасета постов по темам: дизайн

Дата: 2026-08-19

## Задача

Собрать порядка 10 000 постов Threads, найденных поиском по списку тем, и сложить их
в датасет для последующего анализа. Считать статистику будет что-то другое — SQL,
Python, агент; наша задача заканчивается на выгрузке.

Сбор идёт порциями примерно по 1000 постов: около десяти запусков за неделю. Ни
одного длинного марафонского прогона не планируется.

## Решения

| Вопрос | Решение |
|---|---|
| Источник постов | Поиск Threads по списку тем |
| Глубина данных | Только карточка выдачи: автор, текст, ссылка, время, счётчики |
| Кто крутит цикл | Скрипт снаружи, сервис даёт одно действие `search_posts` |
| Хранилище | Отдельная `var/collect.sqlite`, сервисную БД не трогаем |
| Режим | Разовый датасет, накапливаемый за несколько прогонов |
| Выход | Таблица постов плюс экспорт в CSV |

### Почему цикл снаружи, а не фоновая задача в сервисе

Выдача поиска — бесконечный скролл в живой странице, и возобновить скролл между
HTTP-запросами нельзя: каждый следующий запрос начинал бы с начала. Значит 10 000
постов набираются не глубиной одного запроса, а количеством тем: десятки тем по
100–300 карточек. Такой цикл — это `for` по списку с паузами, и городить ради него
машину состояний внутри сервиса не нужно. Прогон на 1000 постов длится 30–50 минут;
переживать отключение клиента ему незачем.

Сервис при этом остаётся тем, чем был: реестром действий без собственной памяти о
том, что кто-то что-то собирает.

### Почему глубина ограничена карточкой

Заход в каждый пост за точными цифрами и комментариями — это 10 000 отдельных
загрузок страниц вместо сотни. Часы работы превращаются в сутки, а профиль нагрузки
становится ровно тем, по которому ловят автоматизацию. Карточка выдачи даёт всё, что
нужно для статистики по темам.

### Риск

Поиск со скроллом выдачи — характерный шаблон автоматизации, и он агрессивнее, чем
150 лайков в сутки, на которые сервис рассчитан сейчас. Риск блокировки аккаунта
выше, чем у всех существующих действий. Снижаем паузами, низким суточным лимитом и
дроблением на короткие прогоны; устранить не можем.

## Действие `search_posts`

Единственное изменение в самом сервисе. Драйвер — браузер: поиск официальным API не
покрыт.

```
search_posts { query: string, limit: 1..300 = 100, sort: "top" | "recent" = "recent" }
  → { query: string, posts: PostCard[] }
```

Открывает страницу поиска Threads, скроллит выдачу, пока не наберётся `limit`
карточек или пока подгрузка не иссякнет, отдаёт плоский список. Состояния между
вызовами нет.

Суточный лимит — 30 успешных вызовов, через уже существующий механизм `dailyLimit`.
Один прогон укладывается в 10–15, так что лимит не мешает работе, но останавливает
зациклившийся скрипт.

Действие попадает и в REST, и в MCP автоматически: оба транспорта читают один реестр.

## Карточка поста

`FeedItem` сегодня — `{author, url, text}`. Для датасета этого мало, поэтому карточка
расширяется до:

```ts
type PostCard = {
  author: string | null;
  url: string | null;
  text: string;
  publishedAt: string | null;  // ISO, из datetime у <time>
  likes: number | null;
  replies: number | null;
  reposts: number | null;
};
```

Числа снимаются с подписей доступности, как и всё остальное в проекте; зацепки живут
в `selectors.ts`. Подписи бывают сокращёнными («1,2 тыс.», «1.2K»), поэтому разбор
выносится в чистую функцию — её и тестируем.

Существующие `read_feed`, `read_profile` и `read_replies` получают новые поля даром:
они ходят через тот же `collectPosts`. Ломающего изменения нет — поля добавляются.

**Отсутствующий счётчик против сломанной вёрстки.** У поста без лайков подписи со
счётчиком просто нет, и это нормальный ноль. Но если на всей странице ни у одной
карточки не нашлось ни одного счётчика — это не выборка из нулей, а переехавшая
вёрстка. Тогда действие падает в `SELECTOR_MISS` со скриншотом, как остальные
браузерные действия. Молча записать 300 нулей в датасет — худший из возможных
исходов: ошибка обнаружится через неделю, когда данные уже посчитаны.

## Хранилище

Отдельный файл `var/collect.sqlite`. Сервисная БД хранит токен и журнал действий, ей
незачем делить место с датасетом; отдельный файл к тому же свободно копируется и
удаляется целиком.

```sql
CREATE TABLE post (
  url          TEXT PRIMARY KEY,
  author       TEXT,
  text         TEXT,
  published_at TEXT,
  likes        INTEGER,
  replies      INTEGER,
  reposts      INTEGER,
  found_by     TEXT NOT NULL,     -- тема, по которой пост нашёлся первым
  collected_at INTEGER NOT NULL
);

CREATE TABLE query (
  text           TEXT PRIMARY KEY,
  last_run_at    INTEGER,         -- NULL, если тему ещё ни разу не собирали
  runs           INTEGER NOT NULL DEFAULT 0,
  last_new       INTEGER,         -- сколько новых постов дал последний заход
  last_error     TEXT
);
```

Посты кладутся через `INSERT OR IGNORE`: один и тот же пост находится по нескольким
темам, и дедуп по ссылке достаётся бесплатно. `found_by` фиксирует первую тему, а не
все — какими ещё словами пост находится, вопрос не этого датасета.

## Ротация тем

Главный механизм, без которого десять прогонов дадут материал одного.

При повторном заходе по знакомой теме выдача почти целиком состоит из уже собранного,
и `INSERT OR IGNORE` его отбросит. Поэтому каждый прогон берёт темы, которые дольше
всех не трогали: `ORDER BY last_run_at NULLS FIRST`. Плюс `sort: "recent"` по
умолчанию — повторный заход приносит появившееся после прошлого раза, а не тот же
топ.

Отсюда требование к списку: **60–100 тем**. С десятью темами десять прогонов
выродятся в один. Список лежит текстовым файлом, по теме на строку, и синхронизируется
в таблицу `query` при каждом запуске: новые строки добавляются, исчезнувшие остаются в
БД вместе с уже собранными постами.

## Скрипт `scripts/collect.ts`

```bash
npm run collect -- --target 1000 --queries queries.txt
npm run collect -- --export dataset.csv
```

Порядок работы:

1. Синхронизировать список тем из файла в таблицу `query`.
2. Брать темы по одной в порядке ротации, звать `POST /actions/search_posts`
   с `limit: 100`.
3. Складывать полученное, записывать в `query` итог захода.
4. Спать случайные 5–15 секунд и брать следующую тему.
5. Остановиться, когда в БД добавилось `--target` новых постов или когда темы
   кончились.

Адрес и токен сервиса берутся из окружения — теми же переменными, что использует
MCP-процесс (`THREADS_API_URL`, `API_TOKEN`).

Ошибки: `RATE_LIMITED` — отступ с растущей паузой и повтор той же темы; `NEEDS_LOGIN`
— немедленный останов с внятным сообщением, дальше идти бессмысленно; `SELECTOR_MISS`
— останов, потому что это поломка вёрстки, и продолжать значит копить мусор. Прочие
ошибки записываются в `query.last_error`, тема пропускается, прогон продолжается.

Ctrl+C безопасен: всё уже записанное лежит в БД, следующий запуск просто продолжит
ротацию.

Экспорт — отдельный режим того же скрипта: выгружает всю таблицу `post` в CSV одним
проходом.

## Тестирование

Браузерные действия в проекте тестами не покрываются: они зависят от живой вёрстки
Threads, и `search_posts` не исключение. Покрываем vitest то, что от вёрстки не
зависит:

- разбор счётчиков из подписей: `«Нравится 1,2 тыс.»` → `1200`, `«1.2K»` → `1200`,
  отсутствие подписи → `null`;
- дедуп и накопление в БД сборщика: повторная запись того же поста не создаёт дубля
  и не сбивает счёт новых;
- порядок ротации тем: ни разу не собранные идут первыми, дальше по давности;
- экспорт в CSV, включая экранирование переводов строк в тексте постов.

## Что сознательно не делаем

- Не заходим внутрь постов за точными цифрами и комментариями.
- Не считаем агрегаты и не рисуем отчёты: на выходе сырой датасет.
- Не делаем планировщик и фоновые задачи в сервисе — запуск руками.
- Не храним историю замеров: пост записывается один раз, перезамер охватов не нужен.
