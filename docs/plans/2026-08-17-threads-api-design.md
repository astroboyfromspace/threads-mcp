# Threads-as-API: дизайн

Дата: 2026-08-17

## Задача

Личный сервис на VPS, дающий агенту программный доступ к одному Threads-аккаунту:
публиковать посты и ответы, ставить лайки, подписываться, репостить, читать ленту и
чужие профили. Один аккаунт, один владелец, не мультитенантный сервис.

## Решения

| Вопрос | Решение |
|---|---|
| Архитектура | Гибрид: официальный Graph API + Playwright, обе части в первой версии |
| Интерфейс | REST как ядро, MCP-сервер тонким адаптером сверху |
| Авторизация браузера | Ручной логин через noVNC на самом VPS, persistent-профиль |
| Стек | Node 22 + TypeScript, Fastify, Playwright, SQLite |

### Почему гибрид

Публикация и ответы полностью покрываются официальным API — стабильный контракт,
не ломается от редизайна, не является нарушением правил. Лайки, подписки, репосты и
чтение ленты официальным API не покрыты вообще, поэтому для них нужен браузер.
Гнать через браузер ещё и постинг означало бы сделать самое частое действие
одновременно самым хрупким и самым рискованным.

### Риск

Автоматизация лайков, подписок и скроллинга ленты через браузер нарушает условия
Meta и является типичной причиной блокировки аккаунта. Риск принят владельцем
осознанно. Дизайн его снижает, но не устраняет: консервативные суточные лимиты,
человекоподобные задержки, отсутствие параллелизма в браузере.

## Архитектура

Один Node-процесс, четыре слоя.

**Транспорт.** Fastify на `127.0.0.1`. Наружу — хостовый nginx с TLS от certbot;
авторизация статическим bearer-токеном происходит в самом сервисе.
Пользователей, ролей и регистрации нет.

**Действия** (`src/actions/`). Единственное место с бизнес-логикой. Каждое действие —
функция `(input) => result`, не знающая, вызвана она из HTTP или из MCP. Здесь же
решается, идти через Graph или через браузер; вызывающая сторона этого не выбирает.

**Драйверы.**
- `src/graph/` — клиент `graph.threads.net`: публикация, ответы, чтение своих постов,
  удаление, квоты.
- `src/browser/` — Playwright, один `launchPersistentContext` на профиль в
  `/var/lib/threads-api/profile`: лайки, подписки, репосты, лента, чужие профили.

**Состояние.** SQLite (better-sqlite3): long-lived Graph-токен со сроком годности,
журнал выполненных действий, счётчики рейт-лимитера.

### Единственный браузер и очередь

Браузер существует в одном экземпляре, и все обращения к нему сериализованы через
очередь. Два параллельных вызова в один профиль — гонка за состояние страницы и
непредсказуемые падения. Запрос к браузерному действию встаёт в очередь; при
переполнении возвращается 429, а не тихое накопление.

## Действия

### Через Graph API

| Действие | Эндпоинт |
|---|---|
| `publishPost` | `POST /{user-id}/threads` + `POST /{user-id}/threads_publish` |
| `replyToPost` | то же, с `reply_to_id` |
| `listMyPosts` | `GET /{user-id}/threads` |
| `listMyReplies` | `GET /{user-id}/replies` |
| `getConversation` | `GET /{media-id}/conversation` |
| `deletePost` | `DELETE /{media-id}` |
| `getQuota` | `GET /{user-id}/threads_publishing_limit` |

Текстовые посты публикуются одним запросом через `auto_publish_text=true`. Посты с
медиа требуют двух шагов: создать контейнер, подождать готовности, опубликовать.
Изображение и видео передаются публичным URL — сервис поднимает временную раздачу
для локальных файлов.

Квоты API: 250 постов, 1000 ответов, 100 удалений за 24 часа. Реальное потребление
сервис читает у самого API, а не только считает локально.

### Через браузер

`likePost`, `unlikePost`, `followUser`, `unfollowUser`, `repost`, `readFeed`,
`readProfile`, `readPostThread`.

Собственные суточные лимиты, заметно ниже человеческого максимума, плюс случайная
пауза между действиями. Селекторы вынесены в один модуль `browser/selectors.ts` —
при редизайне Threads правится одно место.

## Авторизация

**Graph.** Один раз проходится OAuth (`threads.net/oauth/authorize`), короткий токен
меняется на длинный (`grant_type=th_exchange_token`), тот живёт 60 дней и
автоматически обновляется фоновой задачей (`grant_type=th_refresh_token`) при
остатке меньше 10 дней. Токен лежит в SQLite, `client_secret` — в переменных окружения.

**Браузер.** Владелец открывает noVNC, логинится руками, проходит 2FA. Playwright
работает с тем же persistent-профилем. Пароль на диске не хранится. Сервис при старте
и периодически проверяет, жива ли сессия, и при разлогине переводит браузерные
действия в состояние `needs_login`, отвечая на них 503 с понятным сообщением.

## Обработка ошибок

Все действия возвращают единый конверт: `ok`, `data`, `error {code, message, retryable}`.

Классы ошибок: `NEEDS_LOGIN` (нужен ручной вход), `RATE_LIMITED` (локальный или
серверный лимит, с `retry_after`), `UPSTREAM` (Graph вернул ошибку), `SELECTOR_MISS`
(браузер не нашёл элемент — вероятен редизайн), `INVALID_INPUT`.

`SELECTOR_MISS` сопровождается скриншотом в `/var/lib/threads-api/failures/`, чтобы
чинить вслепую не приходилось.

## Тестирование

- Юнит-тесты на слой действий с подменёнными драйверами: проверяют маршрутизацию
  (что публикация идёт в Graph, лайк — в браузер), рейт-лимитер, конверт ошибок.
- Тесты Graph-клиента на замоканном HTTP: двухшаговая публикация, refresh токена,
  разбор ошибок.
- Тест очереди браузера: параллельные вызовы выполняются строго последовательно.
- Ручная проверка браузерных действий на живом аккаунте — автоматизировать её нельзя.

## Порядок работ

1. Скелет проекта, конфиг, SQLite, журнал.
2. Graph-слой и его тесты.
3. Слой действий и HTTP API.
4. Браузерный слой с очередью.
5. MCP-сервер.
6. Деплой: Docker, nginx + certbot, noVNC.
